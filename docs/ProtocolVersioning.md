# クライアント・サーバー間のバージョン整合

7DTD 本体の `NetPackageManager` を逆コンパイルして確定させた事実と、そこから導かれる方針。
調査日 2026-08-12〜13、対象は 7DTD V3.1.0 の `Assembly-CSharp.dll`。

## ゲームが既にやっていること

**パッケージ ID は接続時にサーバーが決め、型名の並びとしてクライアントに配る。**

```csharp
// StartServer(): サーバーが knownPackageTypes を走査して 1..N を割り当てる
// StartClient(): クライアントは空の表で始まる
// IdMappingsReceived(string[] _mappings): サーバーから届いた型名で自分の表を埋める
if (!knownPackageTypes.TryGetValue(_mappings[i], out var value))
{
    Log.Error("[NET] Unknown package type " + _mappings[i] + ", can not proceed connecting to server");
    SingletonMonoBehaviour<ConnectionManager>.Instance.Disconnect();
    GameManager.Instance.ShowMessagePlayerDenied(new GameUtils.KickPlayerData(GameUtils.EKickReason.UnknownNetPackage));
    break;
}
```

ここから次が言える。

| 事実 | 帰結 |
|---|---|
| ID は名前で対応付けられる | **接続後の ID は必ず一致する。誤配送は起きない** |
| クライアントが知らない型名があると入室拒否 | **MOD を入れていないクライアントは、この MOD を入れたサーバーに入れない** |
| 受信時に未知の ID なら `UnknownNetPackageException` | 壊れたデータが書き込まれることはない |
| CRC は MOD のファイルを見ていない | **バージョン違いをゲームは止めない**（実測: DLL も XML も違うクライアントが接続できた） |

拒否時にプレイヤーへ出る文言は `auth_unknownnetpackage`（13言語に翻訳済み）:

> Unexpected data received. Server is either running an incompatible version or requires the client to install mods.

MOD 名までは出ないが、クライアントのログには型名が出るので特定はできる。

## ゲームが見ていないこと

型名の集合だけを見ており、**版数も payload の形式も中身も見ていない**。したがって次は素通りする。

- **既存パッケージの payload 変更** — 名前も ID も同じなので通ってしまい、誤読する
- **意味の変更** — 行き先キーの作り方、列挙型の値の追加。解釈は成功するが食い違う
- **パッケージ外の共有前提** — キーの正規化、アクセスモードの解釈。パッケージ定義のどこにも書かれていない

この MOD は 0.4.16 でキーの正規化を変えている。**そういう変更はパッケージを1つも触らずに互換を壊す。**

## 方針

### 1. 互換を壊す変更をするときは、パッケージ型の名前を変える

版数を付ける（`...Snapshot` → `...SnapshotV2` など）。ゲームが名前で照合するので、これだけで両方向が閉じる。

- **新サーバー × 旧クライアント** → 型名を知らないので**ゲームが入室拒否**
- **旧サーバー × 新クライアント** → 期待する型が `PackageMappings` に無いので、クライアントが検知できる

版数交換の通信を作る必要がない。そして**互換を壊す変更は必ず名前の変更を伴う**ので、版数の上げ忘れという事故が起きない。

### 2. クライアント側で、期待する型の有無を確認する

`NetPackageManager.PackageMappings`（public）に自分の型が含まれるかを見る。通信は不要。

無ければサーバー側の MOD が古いということなので、機能を止めて表示する:

> サーバー側の MOD が古いようです。サーバーと同じバージョンに揃えてください。

### 3. 型名の一覧をユニットテストに固定する

集合が変わればテストが落ち、意図した変更かどうかを必ず問われる。規律ではなく仕組みにする。

あわせて規約として明記する: **既存パッケージの payload を変えるときは、必ず型名も変える。**

### 4. 周知する

Nexus の説明には「マルチプレイではサーバーと全クライアントに導入」と既に書いてあるが、**理由が書かれていない**。実態は「入れないと機能が使えない」ではなく「**入れないと入室できない**」。

追記すべき内容:

- この MOD を入れたサーバーには、MOD を持たないクライアントは接続できない
- サーバーとクライアントは同じバージョンに揃える
- **サーバーを更新すると、更新していないクライアントは入室できなくなる**（パッケージ型が増えた場合）

## パッケージを追加する判断について

型を追加すると、サーバーを更新した時点で**未更新のプレイヤー全員が入室できなくなる**。機能が使えないのではなく、遊べない。

静かに壊れるよりは良い挙動だが、運用上は重い。機能追加のたびに「全プレイヤーに同時更新を強いてよいか」を問うことになる。

**サーバーの記録を変えない機能なら、クライアント側だけで完結させれば通信が不要になり、この代償を払わずに済む。** 設計時にまず検討すること。

## 検証方法

`bin/03-deploy-mods.sh` の `VTT_SERVER_RELEASE_PACKAGE` で、サーバーとクライアントに別ビルドを配備できる。バージョン不一致を意図的に作って確認する唯一の手段。

```bash
VTT_RELEASE_PACKAGE=<新しいzip> VTT_SERVER_RELEASE_PACKAGE=<古いzip> ./bin/03-deploy-mods.sh v3
```

両側のログの `Registered ... as net package id` を突き合わせれば、割り当ての実際が見える（ただしこれは起動時の自前登録であって、接続時にサーバーの表で上書きされる点に注意）。
