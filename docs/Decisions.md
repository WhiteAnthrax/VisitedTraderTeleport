# 判断の記録

この MOD について「なぜ今この形なのか」を残す文書です。**進捗は書きません** — 進捗は腐り、腐った進捗は次に読む人を誤誘導します。現在どこまで進んでいるかは issue と PR を見てください。ここに書くのは、**調べ直さないと二度と手に入らない判断と、その理由**です。

新しい判断をしたら、その都度ここに追記してください。判断が覆ったら、古い記述を消さずに「覆った」と書き足してください。なぜ覆ったかが次の判断材料になります。

---

## 前提: ネットコードが設計を縛っている

**この MOD の設計判断は、ほぼすべてこの1点から導かれます。**

ゲームは接続時に、サーバーが持つネットパッケージの**型名の一覧**をクライアントへ配ります。クライアントは自分が知らない型名があると**入室を拒否されます**。つまり:

- **この MOD を入れたサーバーには、MOD を入れていないクライアントは入れません**(どこにも書かれていない性質)
- **パッケージ型を1つ増やすと、サーバーを更新した瞬間、更新していないクライアントが全員入れなくなります**
- 接続時の CRC は MOD のファイルを見ていないため、**バージョン違いをゲームは止めません**。中身が違っても接続でき、誤読しうります

詳細と実測の根拠は [`ProtocolVersioning.md`](ProtocolVersioning.md)、通信の流れは [`MultiplayerFlow.md`](MultiplayerFlow.md) にあります。

したがって機能を足すときの問いは、常にこうなります — **この機能は、全プレイヤーに同時更新を強いる価値があるか。**

## 判断1: 行き先の削除機能は出さない

**決定**: 実装・実機検証まで終えていたが、リリース前に取り下げ、両系統から revert した(#58 / #59 / #60 / #63 / #64 / #66 / #67)。

**理由**: 削除には6個目のネットパッケージが必要で、上記の代償を全プレイヤーが払う。得られるものは、発端の Nexus 報告にあった「テスト用に湧かせたトレーダーが一覧に残る」というデバッグ操作の後始末で、通常プレイでは起きにくい。さらに、行き先を選ぶと即出発だったものが**アクション画面を挟む形になり、確認を切っているプレイヤーには毎回1クリック増える**。

**残った回避策**: ゲームを終了してセーブフォルダの `VisitedTraderTeleportData.json` を手で編集する。

**覆す条件**: 互換を壊す変更を別の理由でまとめて出すとき、同梱を再検討する余地はある。

## 判断2: 移動コストはクライアント任せのままにする

**決定**: 直さない(#69)。

**現状の挙動**: コスト機能が有効なとき、支払えるかの確認も実際の消費も**クライアント側**で行われる。サーバーは金額を演出パッケージに載せて渡すだけで、検証も徴収もしていない。したがって**改造クライアントは無料で移動できます**。

**理由**: 壊れるものが無く、影響は「自分が入っているサーバーで自分だけコスト設定を回避できる」ことに留まる。一方サーバー側で徴収するには所持品の確認と消費をサーバーで行う必要があり、要求と応答の往復 = パッケージの追加または変更を伴う可能性が高い。前提の代償に見合わない。

## 判断3: 旧形式 TXT のデータは変換しない。ただし読むのもやめたい

**背景**: MOD 0.2.x 以前は `VisitedTraderTeleportVisited.txt` に訪問記録を書いていました。0.3.0 以降は `VisitedTraderTeleportData.json` です。MOD は TXT を**読むだけ**で、書き換え・削除・リネームを一度もしません。

旧形式の行き先には**訪問者が記録されていません**。そのため `GetDestinations` はこれを無条件に一覧へ混ぜており、結果として**アクセスモードに関わらず全員に見えます**。これは README に互換措置として明記された意図的な挙動です(「already available destinations do not suddenly disappear」)。

**決定A: 帰属を決める変換はしない**(#62)。変換すると誰の訪問にするかを機械的に決めることになり、**現に見えている行き先が消える人が出ます**。再訪問すれば自動的に新形式へ移り、そのとき正しい持ち主が付きます。

**決定B: 帰属を決めない移行なら安全**(#70)。TXT の内容を持ち主なしのまま JSON 側へ移し、TXT は読まなくなるだけ(**リネームも削除もしない** — 旧バージョンへ戻したとき壊れるため)。可視性は一切変わらないので、ユーザーから見て何も変わりません。着手には [autotest#30](https://github.com/WhiteAnthrax/7dtd-autotest-tool/issues/30) が前提です。

### ⚠ 訂正済みの誤り

一時期「3.x 系では 2.x のセーブを引き継がないため、旧形式は構造的に存在し得ない」と判断していましたが、**これは誤りです**。The Fun Pimps は V2.6 からの継続を公式にサポートしており、V2.6 のセーブは V3.0 で読み込めます。新規ワールドは推奨であって必須ではありません。

したがって **3.x 系にも旧形式は存在し得ます**(MOD 0.2.x 以前を使い、以来そのトレーダーへ行っておらず、そのセーブを継続した場合)。**3.x から旧形式の読み込みを削除してはいけません。**

## 判断4: 行き先の印(ラベル)はクライアント側に保存する

**問題**: 行き先が増えると同名トレーダーを見分けられません。実セーブで確認済み — 行き先24件、Joel 6人・Hugh 5人・Jen 4人・Rekt 4人・Bob 3人、1ページ5件で5ページ。距離順ソートは既に効いています(`DialogPatches.cs` の `OrderBy(GetDistanceSq)`)が、同名が複数ページに散らばります。

**決定**: 個人用の印をクライアント側に保存する(#71)。**通信が不要なので、前提の代償を払わずに済みます。** これが削除機能と決定的に違う点です。

サーバー側に持たせて共有する案は、パッケージ追加の代償に加えて「持ち主のいない旧形式の行き先に誰の印を付けるのか」という未解決の問いを抱えます。共有は、互換を壊す変更をまとめて出すときに再検討します。

**調査で確定した実装の土台**(V3.2 のアセンブリをデコンパイルして確認):

- **サーバー/ワールドの識別**: `GameIO.GetSaveGameLocalDir()` が `SavesLocal/<GameGuidClient>` を返す。`GameGuidClient` は **GUID** なので、別サーバーが同じセーブ名を使っていても衝突しない。固定マップ(Navezgane 等)では行き先キーも座標も一致しうるため、この区分けは必須
- **キー正規化で印が孤児にならないこと**: `TraderMatching.IsSameTrader` は Core にあり、csproj がソースリンクしているので**クライアント側のアセンブリにも入っています**。必要な材料(`Key` / `DisplayName` / `Position` / `AreaX` / `AreaZ`)はすべて Snapshot で送られているため、キーが変わっても当て直せます

**落とし穴**:

- `GetSaveGameLocalDir()` は `GameGuidClient` 未設定だと**例外を投げます**
- 保存ルートは `GameSaveStorageType`(Roaming / DeviceLocal)で動きます
- **MOD のインストール先に置いてはいけません** — 更新のたびに消えます
- ゲームの `SavesLocal/` に間借りするのも避けるべきです。`archived.flag` / `SaveDataLimit` という整理の仕組みがあり、ゲームの都合で消されうります

**保存の立てつけ**(最初からこう作る。後付けは #70 で苦しんでいるのと同じ問題になります):

1. 場所解決を1つの関数に閉じる
2. 読み取りは候補リストを順に見て、旧い場所で見つかったら現在の場所へコピーして前進する
3. 旧い場所のファイルは消さない(ダウングレードで壊れるため)
4. `SchemaVersion` を書くだけでなく**読む**。既存の `VisitedTraderDatabase` は `SchemaVersion = 1` を宣言していますが、どこからも読まれていません
5. ワールド ID をファイル名だけでなく中身にも持たせる

## 判断5: ゲームの新版が出たときは、配布物で確認する

**決定**: 「新ゲーム版で動くか」を確かめるときは、**今のブランチをビルドしたものではなく、GitHub Releases にある配布済みの zip** を新ゲーム版にかける。

**理由**: ブランチのビルドが通っても、それは「ソースが新ゲーム版に合っている」ことしか示しません。利用者が持っているのは**別のバイナリ**(参照アセンブリが違う)です。逆向きも成り立たず、新ゲーム版でビルドしたものが旧版で動く保証はありません — そしてそれこそが Nexus の「3.0 / 3.1 / 3.2 対応」という表記が主張している内容です。

配布済み zip が新ゲーム版で通れば、**新しいリリースを出さずに対応版数の記載だけ足せます**。V3.2 では実際にそうしました。

手順は [`7dtd-autotest-tool/docs/runbook.md`](https://github.com/WhiteAnthrax/7dtd-autotest-tool/blob/main/docs/runbook.md) の "When 7 Days to Die gets a new version" にあります。

## 未実装で、設計だけ決まっているもの

**バージョン検査**([`ProtocolVersioning.md`](ProtocolVersioning.md) に方針あり、未着手):

- 互換を壊すときは**パッケージ型名を変える**(ゲームが入室拒否してくれる)
- クライアントは `NetPackageManager.PackageMappings` に自分の型があるか確認し、無ければ機能を止めて「サーバー側の MOD が古い」と表示する
- 型名の一覧をユニットテストに固定し、集合の変更を必ず意識させる
- Nexus の説明に「両側必須(入れないと**入室できない**)」「サーバー更新時は未更新クライアントが入室不可」を追記する

プロトコル版数を MOD バージョンと分ける案は**却下**しました。上げ忘れが起きるためです。型名の変更なら、互換を壊す変更が必ず名前の変更を伴うので、事故が起きません。

## 環境の落とし穴

検証環境は**明示的に固定しない限りゲーム版数が勝手に動きます**。

- **Docker 専用サーバーは起動のたびに自動更新されます**(`startserver-with-update.sh` + `STEAM_BETA` 既定値が空 = public)。固定したいなら `.env` に `STEAM_BETA` を明示する
- **Windows クライアントのプロファイル名は版数を表しません**。`3.0Vanilla` という名前でも中身は最新になりえます
- `7DaysToDie.exe` の `ProductVersion` は **Unity のバージョン**であってゲーム版数ではありません

版数の調べ方、ビルド手順、ゲームアセンブリの調査方法は runbook と [`WindowsSshBuild.md`](WindowsSshBuild.md) にあります。
